# ClearSignal WQ 中文设计文档

日期：2026-10-11

状态：设计已批准，等待实施

比赛：Xylem Global Student Innovation Challenge 2026 - Water Quality

## 1. 产品定义

ClearSignal WQ 是一个面向小型水务运营人员和社区水质监测团队的可信异常分诊原型。它不判断水是否可以安全饮用，而是帮助用户回答一个更窄、更现实的问题：传感器出现异常时，应该优先怀疑真实水质变化、传感器漂移、数据完整性问题，还是证据不足，并立即采取什么人工验证动作。

产品的一句话说明：

> Turn noisy water-sensor alerts into explainable, human-verified next actions.

对外英文材料可以使用这句话；本项目的本地设计、计划和开发说明以中文为主。

## 2. 目标用户与核心场景

### 主用户

资源有限的小型水务或社区监测团队中的值班运营人员。他们需要查看 pH、电导率、温度、溶解氧等连续数据，但没有专门的数据科学团队逐条检查异常。

### 核心痛点

- 传感器污损、漂移、校准、断电、卡值和传输中断会产生大量异常。
- 每个异常都升级为污染事故会浪费复测和实验室资源。
- 误报过多又会让运营人员忽略真正需要调查的变化。
- 普通异常检测只显示一个分数，不能说明为什么报警、证据是否可靠、下一步该做什么。

### 单一主流程

用户播放内置站点的一段水质时序，系统发现异常事件，展示证据并给出四类分诊之一；用户查看原因和建议动作，然后把事件标记为“待复测”“待校准”“待检查数据链路”或“已升级实验室确认”。

## 3. 项目目标与非目标

### MVP 目标

1. 使用公开、可复现的真实水质传感器数据建立规则加时序模型的异常基线。
2. 将连续异常点合并为运营人员可以处理的事件，而不是产生逐点告警。
3. 为每个事件输出分诊类别、证据强度、主要驱动因素和人工下一步。
4. 用明确标注的合成场景演示真实水质变化、单传感器漂移和数据完整性问题的区别。
5. 生成可复现的事件级评价报告，并在界面中如实展示限制。

### 非目标

- 不声称检测出具体污染物。
- 不输出“水安全”“可以饮用”或监管合规结论。
- 不替代实验室、合格操作员或应急响应程序。
- 不在 MVP 中接入真实 SCADA、物联网硬件、短信系统或实时外部 API。
- 不把 SWaT 作为必须数据源；未获访问许可时项目仍能完整运行。
- 不使用 LLM 直接决定事件类别。

## 4. 输出契约

每个事件必须输出以下结构：

| 字段 | 说明 |
| --- | --- |
| `event_id` | 稳定、可追踪的事件编号 |
| `start_at` / `end_at` | 事件时间范围 |
| `triage_status` | 四类分诊状态之一 |
| `evidence_strength` | `low`、`medium` 或 `high`，不是伪造的概率 |
| `affected_sensors` | 参与判断的传感器列表 |
| `evidence` | 规则、时序残差、跨传感器一致性和数据质量证据 |
| `recommended_action` | 人工复测、校准、检查链路或升级实验室确认 |
| `data_provenance` | `public_real_data` 或 `synthetic_scenario` |
| `limitations` | 当前结果不能证明的事项 |

四类 `triage_status`：

- `possible_water_quality_event`：多个相关传感器在有效数据窗口内出现一致变化，需要现场复测或实验室确认。
- `sensor_fault_or_drift`：单一传感器出现持续偏移、漂移、卡值或与其他传感器不一致，需要清洁、校准或更换。
- `data_integrity_issue`：时间戳缺口、重复值、无效范围或传输序列异常，需要检查采集和数据链路。
- `insufficient_evidence`：存在异常但证据不足，保持人工观察并安排复测。

任何类别都不得转换成 `safe` 或“污染已确认”。

## 5. 数据设计

### 公开真实数据

第一版使用 `pyhydroqc` 仓库附带的 Logan River Observatory 数据。数据按 15 分钟记录，包含：

- `temp`：水温
- `cond`：比电导率
- `ph`：pH
- `do`：溶解氧
- 可选展示 `turb`：浊度
- 各传感器对应的校正值和质量字段

MVP 固定 `MainStreet2019.csv` 作为主数据：前 60% 时间段用于训练，中间 20% 用于验证，最后 20% 作为冻结测试；切分点遇到连续事件时向最近的事件边界移动。`FranklinBasin2017.csv` 只用于不调参的跨站点稳健性检查。原始数据不复制进公开仓库；下载脚本记录来源、版本和哈希，测试使用小型、允许公开的派生样例。

质量字段和技术人员校正只能作为“传感器数据质量事件”的证据，不能当作真实污染标签。

### 数据切分

- 按时间顺序切分训练、验证和测试，禁止随机打乱造成未来信息泄漏。
- 所有阈值和模型参数只在训练与验证时确定。
- 测试时间段在最终评价前保持冻结。
- 同一异常事件的连续点不得跨越不同切分。

### 合成场景

使用固定随机种子和版本化参数，在真实背景时序上注入三类场景：

1. 多传感器相关变化，用于演示 `possible_water_quality_event` 工作流。
2. 单传感器缓慢偏移或卡值，用于演示 `sensor_fault_or_drift`。
3. 缺失时间段、重复时间戳或无效值，用于演示 `data_integrity_issue`。

界面、评价报告和演示视频必须始终显示“合成场景”标识，不得把场景评价写成真实污染检测准确率。

## 6. 判定架构

系统采用分层、可解释的判定方式：

1. **数据契约检查**：验证时间戳、排序、重复行、采样间隔、必需传感器和数值范围。
2. **规则检测**：识别缺失、越界、卡值、突跳和明显持久异常。
3. **时序基线**：优先使用 `pyhydroqc` 已验证的 ARIMA、动态阈值和事件合并方法；第一版不训练大型神经网络。
4. **跨传感器一致性**：判断异常是否只影响单一传感器，还是多个相关变量在同一时间窗口共同变化。
5. **传感器可靠度**：根据近期缺失、卡值、漂移和校准证据降低对应传感器权重。
6. **分诊规则引擎**：把上述证据组合成四类状态和证据强度。
7. **解释生成器**：从结构化证据模板生成简短说明和人工下一步，不让 LLM添加不存在的事实。

分诊引擎必须是确定性的：相同数据、配置和模型版本必须产生相同结果。

## 7. 系统结构

MVP 使用 Python 单体应用，减少部署和演示风险：

- **Streamlit**：操作界面和演示入口。
- **Plotly**：多传感器时间线、异常区间和证据可视化。
- **pandas / NumPy**：数据契约、切片和场景生成。
- **statsmodels / pyhydroqc 方法**：时序基线与动态阈值。
- **pytest**：单元、数据契约和场景回归测试。

模块边界：

- `data`：下载、校验、切分和数据来源记录。
- `detectors`：规则与时序异常检测。
- `reliability`：传感器可靠度和跨传感器一致性。
- `triage`：四类分诊与证据强度。
- `scenarios`：可复现的合成场景。
- `evaluation`：点级和事件级指标。
- `app`：只负责界面和状态，不承载模型逻辑。

## 8. 用户界面

第一屏直接进入运营工作台，不制作营销首页。

### 顶部

- 站点、时间范围和数据来源。
- 当前运行模式：公开真实数据或合成演示。
- 数据质量摘要和待处理事件数量。

### 主区域

- 左侧：按优先级排列的事件队列，可筛选四类状态。
- 中间：稳定尺寸的多传感器时间线，选中事件后高亮对应时间窗。
- 右侧：事件证据、证据强度、受影响传感器、限制和建议动作。

### 操作

- 播放或暂停内置时序回放。
- 在三个明确标注的合成场景之间切换。
- 将事件标记为待复测、待校准、待检查链路或已升级。
- 打开“为什么这样判断”查看结构化证据。

界面使用颜色加图标和文字三重编码，不能只靠红绿区分；所有文本必须明确区分“异常”“疑似事件”和“已确认污染”。

## 9. 失败与降级

- CSV 缺少字段、时间戳不可解析或采样过短时，停止分析并显示可操作的错误信息。
- 时序模型失败时，退回规则检测，并将结果标记为 `insufficient_evidence`，不得静默继续。
- 某个传感器不可用时，降低证据强度并显示缺失原因，不用其他变量伪造替代值。
- 合成场景参数不合法时拒绝生成，不修改原始数据。
- 应用无需 API 密钥即可运行；任何未来外部服务必须是可选项。

## 10. 评价方案

### 真实数据评价

- **事件召回率**：技术人员标记的传感器质量事件中，被系统识别的比例。
- **事件精确率**：系统事件中与技术人员标记重叠的比例。
- **无效告警率**：干净时间窗口内平均每天产生的事件数。
- **检测延迟**：事件开始到首次告警的时间。

### 场景回归评价

- 三类合成场景必须稳定落入预期分诊类别。
- 改变无关显示参数不得改变分诊结果。
- 相同种子与配置必须生成完全相同的场景和结果。

### 晋级门槛

第一阶段只比较规则基线和 ARIMA 动态阈值。规则基线完成后，根据训练与验证结果把候选模型的数值晋级门槛预先写入总纲，再运行候选模型。只有候选模型在冻结验证集上提高事件召回、且无效告警率没有恶化，才进入最终系统；否则保留更简单的规则基线。测试时间段只在模型选择结束后使用，门槛不得根据测试结果回调。

## 11. 测试与安全

- 数据契约测试：字段、时间顺序、重复行、数值范围和来源哈希。
- 防泄漏测试：训练过程不得读取验证或测试时间窗。
- 单元测试：规则检测、事件合并、可靠度、分诊状态和证据文本。
- 场景测试：漂移、卡值、缺失和多传感器变化。
- 端到端测试：用户能打开工作台、播放回放、选择事件并看到证据和动作。
- 文案测试：页面和导出中不得出现未经确认的 `safe`、`drinkable` 或“污染已确认”。
- 发布前扫描 token、邮箱、本地绝对路径、原始数据和不允许公开的文件。

## 12. 3-4 分钟演示故事

1. **0:00-0:25，问题**：小型团队收到异常，但不知道是污染、传感器故障还是数据问题。
2. **0:25-0:55，正常回放**：展示公开真实数据和当前站点基线。
3. **0:55-1:40，疑似水质事件**：多传感器共同变化，系统给出证据和“现场复测/实验室确认”动作。
4. **1:40-2:20，传感器漂移**：同样出现告警，但只有单一传感器缓慢偏移，系统建议清洁与校准。
5. **2:20-2:50，数据完整性**：展示卡值或时间戳缺口，系统转向检查采集链路。
6. **2:50-3:25，证据与影响**：展示事件级指标、真实数据与合成场景标识，以及减少无效告警的价值。
7. **3:25-3:45，限制与下一步**：强调人工复核、实验室确认和未来小规模现场试点。

## 13. 实施阶段

### 阶段 1：数据与基线

建立可复现下载、固定切分、规则基线和事件级评价。验收后下一步是实现可靠度与分诊逻辑；未通过则缩小为传感器质量复核队列。

### 阶段 2：分诊引擎

实现四类状态、证据强度、解释和人工动作。验收后下一步是接入 UI；若无法稳定区分场景，则移除 `possible_water_quality_event` 自动分类，统一输出 `insufficient_evidence` 加复测建议。

### 阶段 3：工作台与演示

完成事件队列、时间线、证据面板和三个场景。验收后下一步是视觉检查和演示脚本。

### 阶段 4：评价与提交材料

冻结指标、补齐 README、Slides/PDF、3-4 分钟视频和平台项目页草稿。只有平台显示 `Publish` 成功后，总纲状态才能改为 `submitted`。

## 14. 设计验收标准

- 主用户只有一个：资源有限的水质监测值班运营人员。
- 主流程只有一个：异常出现后完成证据查看和人工下一步分派。
- MVP 在无 SWaT、无 API 密钥和无硬件的情况下可完整运行。
- 真实数据、技术人员标签和合成场景在数据、界面和报告中明确分开。
- 模型选择同时考虑事件召回与无效告警率。
- 所有输出都包含证据、限制和人工复核动作。
- 设计不包含未经数据支持的饮水安全或污染识别声明。
